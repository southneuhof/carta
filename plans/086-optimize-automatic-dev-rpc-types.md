## Why this matters

API runtime route changes update during development, but the SDK consumes a
separate generated type snapshot. Developers should eventually get current
RPC types after an API type change without a manual command. The type compiler
must operate independently of runtime route compilation, with measured limits
on CPU contention and update time.

## Issues to fix before enabling

Rows about a future worker describe design risks. They are not failures
observed in today's disabled development workflow.

| Issue | Evidence | Required result |
|---|---|---|
| Wrong destination from simply enabling the flag | Development manifest is under `.sprindle-dev`; SDK export is under `.sprindle` | Publish the actual SDK contract without changing the runtime manifest path |
| Type work blocks runtime publication | `manifest.ts:85` awaits emission before runtime rename | Runtime compilation and restart never await type analysis or emission |
| Repeated cold compiler work | Synchronous config/probe/emit at lines 178, 221, 329; fresh temporary project; incremental disabled | Reuse validated compiler state or stable incremental build inputs in a separate process |
| Missing type-only dependency events | Runtime esbuild input map and the fixture above | Type watcher follows TypeScript-selected dependencies, including external type-only sources |
| Startup with no frontend contract | API dev declarations are disabled; SDK imports the generated file | Produce a real first contract and report types as pending until it exists |
| Edits can accumulate behind compilation | Serial runtime queue with per-event jobs | Type queue retains the latest pending revision and does not publish an older revision afterward |
| Type errors can stop runtime updates if coupled | Inline emitter failure rejects the route compile | Keep runtime live; retain the last valid type graph and report the current type error |
| Parallel publishers can restore older types | Existing batch builds plus a new independent worker share one pointer | Serialize publication and validate source identity before changing the pointer |
| Weak reuse can hide changed types | Existing cache includes compiler/config/resolution and type inputs | Keep the complete correctness key and dependency-resolution invalidation |
| Background work can still slow routes | Worker shares host CPU and memory with route compilation/server | Pass same-host baseline/candidate latency checks before default enablement |
| Stale tooling or orphan workers | Compiled module is loaded once; new worker adds another lifecycle | Use Plan 082 preparation and shut down every worker before replacement |

## Steps

### 1. Measure the disabled baseline and verify compiler feasibility

Create the isolated real-process benchmark before selecting an incremental
executor. Measure runtime compile completion, edit-to-HTTP readiness, cold API
readiness, and eventual type publication separately. Use actual tooling and
an API-shaped route/type graph, not a sleep or mocked compiler. Record Node,
compiler, host, route count, dependency graph shape, and source revision.

Inspect the installed TypeScript 7.0.2 declaration capabilities. Prove the
candidate can emit the current contextual overlay and update declarations
after an edit without reconstructing its full compiler state each time.
Do not assume the editor snapshot API can emit. A supported persistent CLI
watch/incremental executor is an acceptable fallback if measured. Keep its
work in the type child process.

**Verify:** run the command-table disabled baseline command; it exits 0 and
records raw samples. Run `pnpm --filter @southneuhof/sprindle exec vitest run src/tooling/declarations.spec.ts`;
the compiler experiment emits types accepted by a real consumer before and
after a type-only change. Record the supported executor
and measured cold/warm costs here. Stop if no executor can meet the stated
limits; keep declarations disabled.

### 2. Share declaration logic and protect publication

Move the existing emitter and declaration-input proof into
`declarations.ts`. Keep batch build behavior, full cache keys, contextual
helpers, path alias rewriting, portable sibling types, and immutable version
trees. Use one declaration producer for batch and development.

Add publication coordination for the shared contract pointer. Complete a
version tree before renaming the pointer. Serialize publishers, then recheck
the source identity before publication. A later-source job must not be
overwritten by an earlier job that finishes late. Failed jobs preserve the
last valid graph; do not certify its metadata as current for failed inputs.

**Verify:** `pnpm --filter @southneuhof/sprindle exec vitest run src/tooling/manifest.spec.ts src/tooling/tooling.spec.ts src/tooling/declarations.spec.ts`
passes, including existing unchanged-cache and active-reader tests. Concurrent
batch jobs prove the shared publisher leaves the latest valid source revision.

### 3. Add the independent persistent type worker

Expose `watchRouteDeclarations` from the existing tooling entry.
It starts one child process, reports type success/error/pending state, and
returns an awaited close handle. Bundle the internal worker with the normal
package producer; do not add a command the developer must remember.

Reuse the executor proved in Step 1. Use a stable ignored working area under
`.sprindle-dev/types-work` for overlay projection and incremental state.
Write only changed projected files and remove deleted ones. Preserve logical
source paths in diagnostics. Invalidate state when configuration, compiler,
resolution, or route/scope structure requires it.

Watch the TypeScript dependency graph and local configuration, including
type-only imports outside routes, sibling workspace sources, ambient types,
and resolution changes from new files. Refresh selected dependency paths
after changes. Preserve logical/real-path handling and delete/recreation
recovery. Watch external directories only at the required depth. Do not
recursively watch all dependency or generated trees.

Coalesce edits into the latest pending type revision. Type work and its
success/error callbacks must not call runtime compilation or request a server
restart. Bound CPU/concurrency; moving work into a process alone is not a
performance result.

**Verify:** `pnpm --filter @southneuhof/sprindle exec vitest run src/tooling/manifest.spec.ts src/tooling/tooling.spec.ts src/tooling/declarations.spec.ts`
passes for type-only edits,
new resolution candidates, scope changes, failed-type recovery, rapid edits,
worker shutdown, and concurrent batch/worker publication. The installed-package
proof starts the bundled worker
through normal Node without source execution flags.

### 4. Prove API development and SDK behavior together

Create an isolated API/SDK fixture using the actual development entry,
runtime compiler, type worker, and copied SDK source. Its synthetic server
needs no database. Compile valid and invalid consumers with the frontend's
installed TypeScript compiler.

Cover first contract creation, changed request/response types, external
type-only edits, route add/move/delete, rapid edits, type errors and recovery,
and concurrent standalone route builds. Observe the final SDK behavior.
Observe unchanged runtime compilation for type-only edits. Observe API
availability and route updates while type generation runs or fails.

For this step, the owned fixture runner starts the actual development process
and the public `watchRouteDeclarations` handle together, then closes both.
Do not edit copied production source to insert calls. The runtime path remains
`.sprindle-dev/routes.mjs` with `declarations: false`. The worker
publishes types to `.sprindle/routes.d.ts`. Add the production lifecycle
hook in Step 6; leave normal development disabled through the speed gate.

**Verify:** `node --test apps/api/scripts/dev-rpc-types.proof.mjs`
and `pnpm --filter @southneuhof/api test:dev-routes` pass.
The fixture proves one initial runtime compile, independent type failure,
no missing referenced declaration files, and full process cleanup.

### 5. Pass the latency gate before default enablement

Use the same benchmark source, host, Node, and dependency installation for
disabled and candidate modes. Alternate runs to reduce warm-cache/order bias.
Select the real producer composition in the owned benchmark runner; add no
production flag solely for testing.
Use at least two rounds of 20 warm edits per mode and five cold starts per
mode. Record raw samples, median, p95, peak memory, and final source identity.
Include a representative large route graph, external type-only edits,
runtime edits while the type worker is busy, and route moves.

Proposed acceptance limits:

- Runtime compile and edit-to-HTTP medians increase by no more than
  `max(50 ms, 5% of baseline)`.
- Their p95 values and cold API readiness increase by no more than
  `max(100 ms, 10% of baseline)`.
- Warm type updates reach a usable current SDK contract within 1 second at
  p95; cold first-type publication completes within 5 seconds.
- No stale final publication, duplicate runtime compile, unbounded queue,
  or surviving owned process occurs.

These are proposed engineering limits, not measured current behavior. Treat
them as measurement tolerances. Investigate a repeatable runtime regression
even when it falls within a tolerance. Report any failure and keep the default
off. Do not relax a limit silently, exclude
busy-worker samples, or count consumer-test duration as route compilation.
Repeat once for material measurement noise and report both results.

**Verify:** `node packages/sprindle/test/declaration-latency.proof.mjs --output plans/development-workflow/rpc-types-benchmark.json`
exits 0 and records all raw samples and limits. Review the report with the
correctness evidence before Step 6.

### 6. Enable the proved worker and close the deferred task

Only after Steps 1–5 pass, start the independent worker by default from normal
API development. Add awaited worker shutdown and framework-replacement cleanup
in `dev.ts`. Change the API proof to invoke that normal entry directly;
remove its separate worker start so it cannot hide a missing production hook.
Keep inline declarations disabled. Report a bounded pending
state on cold type startup, a current type error after failure, and readiness
after successful publication. Do not present an old contract as current.

Run stable correctness proofs in CI. Keep machine latency comparisons as
recorded performance evidence rather than flaky wall-time assertions on a
shared CI runner. Document live RPC updates and standalone build/check
freshness. Reconcile Plan 084's canonical guard; it must work without a worker.

**Verify:** run the remaining command table, review scope and measurements,
then mark this plan and its index row complete with links to the benchmark
and test evidence. A failed or missing performance gate leaves it deferred
and development generation disabled.
