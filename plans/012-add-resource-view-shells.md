## Why this matters

Removing CRUD wrappers entirely would force Cards, headers, actions, and feedback into Form/Table/Detail, damaging their generality. The replacement is a thin family of view shells: consistent application chrome with explicit slots and declarative controls, while the core props remain directly bindable.

## Current state

- `CRUDCreate.vue:34-69` and `CRUDUpdate.vue:34-72` render Card/header/back navigation around Form and select create/update behavior.
- `CRUDList.vue:192-281` renders create, detail, update, delete, filtering, and export controls around Table.
- `CRUDDetail.vue` combines print layout, action chrome, data injection, and Detail.
- Target mapping: `CRUDList -> ListView + Table`; `CRUDDetail -> DetailView + Detail`; `CRUDCreate/CRUDUpdate -> FormView + Form`. Shells accept named slots/typed control descriptors and normal Vue event handlers, not an `actions` object threaded through a `state` prop.

## Steps

### Step 1: Define shell responsibilities and shared control contract

Define a small typed control descriptor for extraordinary/custom controls (identity, label/icon, placement, disabled/loading, handler or navigation target). Standard controls will later be generated by resource capabilities; shells simply render descriptors and named slots. Do not add a generic mutable action/state protocol.

Define common shell slots such as header, primary controls, secondary controls, filters, body, footer, and error/feedback where appropriate.

**Verify**: type tests reject data loaders/resource runtimes on shell props and accept ordinary Vue handlers/links.

### Step 2: Implement ListView

Render the established Card/page-title/toolbar/filter/body layout. Accept Table props through a direct `table` prop bag or body slot and forward them without translation. Support empty/loading/error presentation only when supplied by the core/body; do not duplicate Table state.

**Verify**: mount tests assert Card/header/control placement, prop forwarding identity, slot overrides, and absence of router/runtime calls.

### Step 3: Implement DetailView

Render detail Card/header/back/edit/delete/print regions as configurable controls/slots. Accept and forward Detail props unchanged. Preserve print-friendly extensibility without embedding the current CRUD resource lookup.

**Verify**: tests cover default chrome, hidden controls, custom controls, print slot, and exact Detail prop forwarding.

### Step 4: Implement FormView

Render Form inside consistent Card/header/back/submit/cancel feedback chrome. Receive Form props unchanged and wire submit/reset through Form's exposed contract/events. It must not know whether submission creates or updates.

**Verify**: identical FormView tests run with create-like and update-like Form props; neither shell nor Form receives mode.

### Step 5: Add visual/accessibility regression coverage

Use semantic DOM tests (and screenshots if the repo's test stack supports stable snapshots) to lock headings, keyboard order, accessible names, disabled/loading behavior, and narrow viewport layout. Avoid brittle full-markup snapshots.

**Verify**: framework full tests/type-check pass and existing web screens remain unchanged.

## Test plan

- Unit/mount tests for each shell's slot and control behavior.
- Prop-forwarding identity tests proving no adapter transformation.
- Accessibility tests for heading hierarchy, buttons/links, focus order, and feedback regions.
- Negative dependency test/static assertion that shells do not import project stores/router/runtime.

## Done criteria

- [ ] Three shells provide CRUD-looking layout without entering core components.
- [ ] Core prop bags are forwarded unchanged.
- [ ] No shell fetches data or resolves resource operations.
- [ ] Controls are declarative Vue props/slots/events, not action-state or commands.
- [ ] Legacy screens remain unchanged and validation passes.
- [ ] Index row is `DONE`.

## STOP conditions

- A shell needs direct project router/permission/RPC imports.
- Shell state duplicates Table/Detail/Form data state.
- Standard appearance cannot be matched without modifying core components.
- The control contract grows into a workflow interpreter.

## Maintenance notes

Shells are visual policy, not application policy. New domain workflows should be composed in route Vue code through slots and handlers.
