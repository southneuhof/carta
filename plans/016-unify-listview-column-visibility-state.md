## Why this matters

Rapid column toggles currently perform multiple copies and a synchronous storage write for every click. `ListView` owns `visibleColumns`, `useTablePreferences` owns `visibleKeys`, and controlled `Table` owns another local `visibleColumns` copy. One click crosses all three layers before TanStack rebuilds visible headers/rows/cells.

Keep exact user flow: a switch immediately shows or hides its column. Make `useTablePreferences.visibleKeys` the single mutable source for ListView. ListView passes it directly to Table; Table reads a controlled prop directly rather than mirroring it. Preference writes are trailing-debounced and flushed on unmount, so rapid clicks persist only final state without losing it.

## Steps

### Step 1: Make preference visibility ListView's only mutable state

In `ListView.vue`, remove local `visibleColumns` and its preference watcher. Read `columnPreferences.visibleKeys` directly for Switch model values, exports, Table's `visible-columns` prop, and column-reset synchronization. Keep a named `setVisibleColumns()` boundary for Table's update event; it normalizes against `columnKeys` then calls `columnPreferences.setVisible()` exactly once.

The existing zero-visible-column guard remains in that boundary. A Switch click must still cause visible Table headers/cells to update immediately; it must not create a draft or require Apply.

**Verify**: existing one-toggle view test remains immediate after adaptation.

### Step 2: Stop controlled Table from mirroring visibility props

In `Table.vue`, replace mutable controlled `visibleColumns` state and `props.visibleColumns` watcher with a derived value: controlled Table reads `props.visibleColumns` directly; uncontrolled Table reads its own preference value. `setVisibleColumns()` writes only uncontrolled Table preferences, then emits normalized value for callers.

Build `columnVisibility` from a `Set` of the derived keys, not repeated `Array.includes()` scans. Keep all existing controlled/uncontrolled behavior, field-key filtering, and `update:visibleColumns` public event. Do not move ListView logic into Table.

**Verify**: controlled Table test proves prop updates render immediately and make no local storage write.

### Step 3: Debounce visibility persistence without delaying state

In `useTablePreferences.ts`, keep `visibleKeys.value` assignment synchronous in `setVisible()`. Replace direct `persistVisible()` call with a single trailing timer (150–250 ms); each new click cancels/restarts timer. Flush pending visible preference once in `onBeforeUnmount` and clear timer. `resetColumns()` must cancel a pending write before removing storage, preventing stale pre-reset visibility from being written later.

Do not debounce `sizes`, use `requestAnimationFrame`, add storage copies, or alter stored JSON schema.

**Verify**: rapid visible updates produce no write before timer expiry, then one write containing final ordered visibility; unmount before expiry flushes final state once.

### Step 4: Add characterization coverage

In `views.spec.ts`, use a namespaced two-column ListView and a localStorage spy/helper:

- Rapid switch clicks update headers immediately after each click.
- No `visible-columns` storage write occurs before debounce expiry.
- Expiry writes exactly once with final visibility.
- Reset cancels a pending write and does not resurrect pre-reset storage.

In `table.spec.ts`, retain/extend controlled visibility test to prove the core component reflects external props immediately without allocating an internal controlled source or writing preferences.

Use fake timers only around debounce assertions; restore real timers in `finally`/cleanup. Assert storage key and payload, not elapsed-performance metrics.
