## Why this matters

Rapidly toggling columns can freeze or crash a populated ListView. This is not an event loop: it is repeated synchronous work on every switch click. `ListView` currently applies each selection immediately, persists it synchronously, then sends new arrays through a controlled `Table` prop chain. Each click rebuilds TanStack visibility and rerenders the table while the column dialog also rerenders.

The fix must separate cheap dialog editing from expensive table application. Switches modify a local draft only. The user applies the draft once; that one boundary updates `visibleColumns`, persists namespace preferences, and lets `Table` rebuild its visible rows/cells once. Closing or cancelling discards draft edits.

## Steps

### Step 1: Make dialog switches edit a local draft

In `ListView.vue`, add `draftVisibleColumns` beside committed `visibleColumns`. When Columns dialog trigger opens, copy committed visibility into draft. Replace inline switch array construction with a named draft-toggle helper. It must preserve source-field ordering and existing rule that an actionless table cannot have zero visible columns.

**Verify**: focused test initially fails after changing the existing immediate-update expectation.

### Step 2: Add explicit Apply and Cancel boundaries

Use Dialog content/footer `setOpen` slot binding. Add Apply button that calls existing `setVisibleColumns(draftVisibleColumns)` once, then closes dialog. Add Cancel button that closes without calling `setVisibleColumns`. Keep Reset columns' current immediate reset behavior; after reset, synchronize draft from committed visibility so dialog controls remain accurate.

Do not debounce `setVisibleColumns`, write to localStorage from draft state, or alter Table. Draft editing must have zero Table prop changes and zero preference writes.

**Verify**: table remains unchanged while switches toggle; it changes only after Apply.

### Step 3: Replace interaction coverage

In `views.spec.ts`, replace `updates visible columns as soon as a column switch changes` with tests using a namespaced two-column table and a localStorage spy/helper:

- Repeated switch clicks change draft controls but leave table headers and `visible-columns` storage writes unchanged.
- Apply after a draft hiding `status` produces one visible header and exactly one persisted preference write.
- Cancel/close after a draft edit leaves committed headers and storage unchanged; reopening starts from committed visibility.
- Reset retains existing behavior and leaves dialog draft synchronized.

Follow existing `mountCore`/`flush` setup. Do not add timing assertions or performance thresholds; assert the architectural boundary (no commit/work before Apply) directly.

**Verify**: focused views test passes with all new cases.
